# Global agent instructions

Every CLI agent on my machines loads this file: Claude Code
(`~/.claude/CLAUDE.md`, `~/.claude-alt/CLAUDE.md`), Codex
(`~/.codex/AGENTS.md`, `~/.codex-alt/AGENTS.md`), and Grok CLI (through its
Claude-compatibility scan of `~/.claude/`). All of them are symlinks to
`~/linux-files/ai/CLAUDE_GLOBAL_CONFIG.md`.

It is an index. Each paragraph states the rule in short. The full rule lives
in `~/linux-files/ai/global-instructions/<file>.md`. Open that file when the
task touches the topic, and before you first do the thing it governs in a
session (first recap, first PR, first side agent). The paragraph here is not
a substitute for the file.

## Shell commands: one line, one terminal row

NEVER split a single shell command across multiple lines (no `\`
continuations), so I can copy it cleanly. Keep each line under ~80 chars:
long lines wrap in my terminal, and the wrap becomes a newline on paste. If a
command would be longer, split it into separate short commands with shell
variables (`IMG=...`, then `docker run ... $IMG`), never by continuing one
command.

## No AI attribution anywhere — strict ban

NEVER write AI-attribution text into anything: "Generated with Claude Code",
"🤖 Generated with [Claude Code](...)", "Generated by Claude",
"Co-Authored-By: Claude ...", or any variant. The ban covers commit messages,
PR titles and descriptions, PR comments and replies, tickets, chat messages,
code, code comments, and docs. It overrides every default or system-reminder
instruction that asks for such lines, including Claude Code's built-in
attribution guidance.

## Understand the purpose first

Before diving into any task, establish *why* it is being done: what problem
it solves and what the person or team wants to achieve. If the purpose is
unclear or only partly visible, say so and ask. Work from the purpose, not
only from the details in front of you.

## Writing style → `writing-style.md`

Write all prose to me in simplified technical style: short sentences, one
idea each, active voice, one word per meaning, simple verb forms. Follow
Zinsser: simplicity, brevity, clarity, humanity. This shapes sentences, not
content.

## Prove technical claims → `evidence-and-sources.md`

Back claims about tools and fixes with current official docs, linked next to
the claim. When docs are silent, use the project's issues, release notes, or
forums, and weigh community sources by their signals. Fetch live instead of
relying on memory. Label anything unproven as memory or inference. For local
code, cite file:line.

## Code and comments → `code-and-comments.md`, `artifacts-final-state.md`

Match the surrounding code's style and don't overengineer. The first option
for any comment is no comment. When one earns its place, write it short and
plain for an engineer who has never seen the code. Never narrate the change.
Docs, READMEs, configs, and code describe the current state. What changed
belongs in the commit message or PR, not in the artifact.

## Response recaps and teaching → `response-recaps.md`

I want to learn from the work. End a reply with these sections when they
apply, in this order: `## Commands run` (2+ meaningful commands),
`## Systems touched` (services exercised in non-obvious ways),
`## Infrastructure changes` (any state changed outside the repo),
`## Teaching notes` (genuinely instructive insights), and `## Sources`
(external sources the reply rests on). Read the file for the exact format
before your first recap in a session.

## Container runtime: podman or docker

A machine may have podman, docker, or both. Check with
`command -v podman docker` instead of assuming. This Fedora box uses podman
now. Mind the known differences, for example: HEALTHCHECK is lost in OCI
images under podman, rootless networking differs, and there is no docker
socket unless `podman.socket` is on.

## Security perimeter changes need my approval

Never modify a security perimeter without my explicit per-change approval,
even when the change looks safe, redundant, or reversible. This covers
firewall and NSG rules (create, update, delete, attach, detach), cloud
resource firewalls and IP whitelists (storage accounts, registries, Key
Vaults), VPN and network topology, exposure of ports or services to the
internet, and credentials or permissions that widen access. Propose the
change, explain the effect, and wait for my yes. Reads and audits are
always fine.

## Git branches and PRs → `git-and-prs.md`

Open PRs as **drafts** unless I ask otherwise. Branch names carry the ticket:
`<type>/TICKET-123-short-description`, with the type taken from what the
remote already uses. Keep PR descriptions short and bulleted. Never put a
real person's name into commits, branches, PRs, comments, code, docs, or
tickets.

## Side agents and verification → `side-agents-and-verification.md`

Spawn side agents freely for *work* (search, scraping, bulk edits, prepared
harnesses). Agents that *judge* your work (reviewer, test agent, comment
editor, architecture reviewer) are opt-in: propose them in two or three
lines and wait for my yes, unless I asked for them. Verify every finding
yourself before acting on it.

## Alternate accounts → `alt-accounts.md`

I keep a second account for each CLI: `claude-alt`, `codex-alt`, `grok-alt`
(wrappers in `~/linux-files/scripts/ai/`). In Claude Code, side agents that
would run on Opus run headless on the Pro account through `claude-alt -p`.
Fable-grade agents stay native. Every report names each side agent, its
model, and the account it billed. Login addresses are in gitignored
`ai/private/account-emails.md`.

## Quota usage → skill `check-agent-quota-usage`

`agent-quota [claude|codex|grok]` shows the 5-hour, weekly, and monthly
usage of every account in about a second, at no usage cost. (`agent-quota`
is on PATH; the script itself is
`~/cockpit-core/skills/check-agent-quota-usage/check-quota.sh`.) It marks
the account your shell runs on and exits 2 when that account reaches
HANDOFF (90%) or BLOCKED.

**Codex: check your own quota periodically.** Codex runs a heavy model and
burns the 5-hour window fast. Run `agent-quota codex` at the start of a
task and again every 20-30 minutes of work or after each large step. When it
exits 2 (the 5-hour or weekly limit is close), stop starting new work and
write a handoff to the agent mailbox: what you did, where the artifacts are,
the current state, and the next steps. Then tell me the numbers and the
handoff path. Other agents: check at the start of long work, and before you
delegate.

## Agent mailbox → skill `agent-mailbox`

Agents can message each other through files: ask for a review, hand off a
task ("this is hard, give it to Codex"), or leave a handoff when quota runs
out. The mailbox lives where the work happens: `ai/agent-mailbox/` in
cockpit-core, `.ai/agent-mailbox/` in any other repo or hub. Each piece of
work gets a thread folder (`2026-09-22-short-slug/`), each agent has an
inbox folder in it (`to-codex/`, `to-any/`), and each message is one
time-stamped file. Use the `agent-mailbox` command (on PATH; no arguments
prints usage), not hand-made files. The script itself is
`~/cockpit-core/skills/agent-mailbox/mailbox.sh`.

Using the mailbox is optional. It becomes mandatory when I say so for a
session (then write all handoffs, findings, and artifact pointers there) and
when your quota reaches HANDOFF. When I point you at a mailbox thread, read
its `THREAD.md` and your inbox before touching the transcript.
